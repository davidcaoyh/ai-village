# Decision log

One entry per non-obvious choice, in the format **decision -> alternatives -> why**.
Entries are written when the choice is made, not reconstructed at the end.
Several carry numbers measured on live calls; those are dated.

| # | Decision | Alternatives considered | Why |
|---|---|---|---|
| D1 | Reach all models through OpenRouter (one OpenAI-compatible API) | native SDK per provider; LiteLLM proxy | One client, one key, one spend dashboard; swapping a model is a config edit. ~5.5% fee is irrelevant at this scale. Isolated in `village/llm.py`, so reverting is a one-file change. |
| D2 | No agent framework; a hand-written ~150-line loop | LangGraph, CrewAI, AutoGen | The loop is small, and writing it is exactly the skill being screened for. When an agent misbehaves you debug your own code, not a framework's abstraction. Frameworks win on large teams and complex graph workflows; neither applies here. |
| D3 | Turn-based round-robin scheduling | true async concurrency | Reproducible bugs, readable conversation order, one budget knob. The real village is concurrent - listed as future work. |
| D4 | Event-sourced SQLite; one append-only `events` table is the only state | ORM with per-entity tables; Postgres | UI, replay, debugging, and analysis all become queries over one table; nothing can drift out of sync. SQLite = zero ops, one file to back up. |
| D5 | FastAPI + WebSocket + single vanilla-JS page | React + build step; HTTP polling; SSE | The frontend is a log viewer. A build pipeline buys nothing and costs POC hours. SSE would also have been fine. |
| D6 | Memory = rolling window + agent-written notes + periodic self-compaction | full history in prompt; vector-DB retrieval | Prompts cannot grow forever - cost rises and quality falls. Compaction is the same pattern Claude Code uses. Retrieval is the natural v3. |
| D7 | Safety rails from day 1: no shell tool, untrusted-data framing on fetched content, no contacting real people, spend + turn caps | add them after the demo works | The real village hallucinated a 93-person contact list and sent ~300 spam emails. Anticipating those is the difference between a toy and a system. |
| D8 | Cast defined entirely in `configs/agents.yaml` | agents constructed in Python | Adding a villager or running a hero session on bigger models is a config edit. Also makes runs comparable: one thing changes at a time. |
| D9 | Cost read from `usage.cost` on the response; no local price table | hardcoded per-model $/token table; recompute from `/models` pricing | OpenRouter returns `cost` (USD) on **every** response with no request flag (the old `usage: {include: true}` is deprecated and ignored). A local table silently drifts the day a provider reprices; the provider's own number cannot. Verified Aug 16, 2026 on a live call: `usage.cost = 0.0001229`. |
| D10 | Reasoning **suppressed** per agent (`reasoning: {effort: ...}` in `agents.yaml`); `reasoning_details` **not echoed** across turns | echo `reasoning_details` verbatim (OpenRouter's recommendation for multi-turn tool calling); leave reasoning at provider default | Measured on `openai/gpt-5-nano`: 256 of 299 completion tokens — **~83% of the call's cost** — went to hidden reasoning before emitting a 12-word tool call. Villagers select one action from a 7-tool menu; that is not reasoning-hard work. Dropping also helps correctness: an agent acts once per turn against a world that changed since it last spoke, so resuming stale reasoning is a liability, not continuity. And 4 models from 4 families emit this field in 4 shapes — echoing means 4 code paths through the hottest function. **Counterpoint:** on a genuinely multi-step chain (search → read → decide), echoing measurably improves coherence, and that is the version to build for a research-grade run. `llm.py` still *returns* `reasoning_details`, so the policy lives in `agent.py` and flipping it is a few lines. Note `exclude: true` only *hides* reasoning — you are still billed; only lowering `effort` reduces tokens. |
| D11 | Strip reasoning blobs from `raw` before persisting to the event log | log the provider payload verbatim | `reasoning_details[].data` is an encrypted chain-of-thought thousands of characters long. Measured on one real turn: stripping took the logged payload from 6,244 → 1,999 bytes (**−68%**). Over ~480 turns that dominates the SQLite file and slows every replay query (D4). The human-readable `reasoning.summary` is kept (truncated to 2,000 chars) because it genuinely helps when debugging why an agent chose an action. |
| D12 | Search backend: Tavily when `TAVILY_API_KEY` is set, DuckDuckGo (`ddgs`) otherwise | Tavily only; DuckDuckGo only; a paid SERP API | The fallback means anyone can clone the repo and run it with zero accounts - which matters when the person evaluating you tries it. Tavily is preferred when present because its snippets are written for LLM consumption and are markedly cleaner, which directly reduces tokens. |
| D13 | `tools.execute()` never raises; every failure returns an observation string | let exceptions propagate and fix the prompt | A 404 at turn 60 would kill a session you paid for, and the agent would very likely have recovered on its own. This is the same transport-failure vs. model-mistake distinction `llm.py` already draws, applied one layer up. Arguments are bound with `inspect.signature().bind()` *before* the call so a missing key is named rather than surfacing as a `TypeError` from inside a tool. |
| D14 | `end_turn` signals via a flag on `ToolContext`, not an exception | raise `TurnEnded`; return a sentinel string the loop string-matches | An agent choosing to stop is the normal end of a turn, not an error - control flow that reads as an error path invites someone to log it as one. And `execute()` must never raise (D13), so an exception would be the one inconsistency in the module. |
| D15 | The assistant message is **reconstructed** from normalized fields before being appended to the conversation | echo `resp.raw["choices"][0]["message"]` back verbatim | The raw message carries provider-specific extras (reasoning blobs, the `reasoning_summary` we add in D11) that some providers reject on the way back in. Rebuilding from `{id, name, arguments}` keeps the conversation provider-neutral, which is the entire promise of `llm.py`. Cost of getting this wrong: an intermittent 400 that only appears on multi-step turns. |
| D16 | Each turn's prompt is **rebuilt from the event log**, not carried as a growing message list | keep a persistent per-agent message list in memory | Three things fall out for free: a crashed process resumes exactly where it stopped, every turn's context is reproducible from the database, and the window can never quietly grow past its bound. Costs a little assembly work per turn. |
| D17 | Events are **rendered as prose lines** into the prompt, not dumped as JSON | JSON-serialize the event rows | A model reads `[claude] we should split the sources` far more reliably than a nested object, at roughly a third of the tokens. `memory._describe()` is the single place that decides what history looks like to an agent - the first place to tune when behaviour disappoints. |
| D18 | A turn is bounded by `max_steps` (default 6); no tool call twice ends the turn | let a turn run until `end_turn` | An agent will occasionally loop on a failing tool. Bounding a turn keeps one confused villager from eating the whole session budget. Hitting the cap is logged (`step_cap_reached`) rather than silently swallowed, because a villager that regularly hits it is a *prompt* problem, not a code problem. |
| D19 | Four independent stop conditions: turn cap, spend guard, human kill switch, KeyboardInterrupt - all exiting through one `finally` that writes `session_end` | rely on the turn cap alone | An autonomous loop that spends money needs more than one way to end, because the failure you did not anticipate is the one that runs all night. Single exit path means a session always ends with a `session_end` event: a session that merely stops emitting events is indistinguishable from a crash six weeks later. The kill switch takes effect at a turn boundary, not mid-turn, so the log never contains a tool call with no result. |
| D20 | The kill switch is stored as an **event**, not a flag column or a signal | a `sessions` table with a `stopped` boolean; a Unix signal | "Who stopped this session, and when" becomes answerable from the same log as everything else. One source of truth means one place to look (D4). |
| D21 | The web server **cannot start a session** - two processes, one SQLite file | one process serving HTTP and running the village | A crashed browser tab, a reload, or a uvicorn restart cannot disturb a paid-for run, and a viewer can attach to a session that is already three hours old. WAL mode lets the server read while the orchestrator writes. |
| D22 | The socket **polls** SQLite every 0.7s rather than being notified | a queue/pubsub between orchestrator and server | Two separate processes would need real infrastructure to pass notifications; polling an indexed `(session_id, id)` read is cheap. Right at four agents, wrong at four hundred. |
| D23 | Human messages are `system` events with `kind=human_message`, and rate-limited to one per 20s | append them as `chat` events from a fake agent | The log must never blur what a *model* said with what a *person* said - six weeks later that distinction is the whole dataset. The rate limit exists because a viewer who can type continuously turns the village into a chat toy and the transcript stops being evidence of anything. |
| D24 | Tests drive the loop through an injected `chat_fn`, so the whole suite runs offline | integration tests against the live API | A test suite that needs an API key is a test suite you stop running, and an agent system whose loop can only be exercised by spending money is one you cannot refactor. 33 tests, no network, ~1s. |
| D25 | A tool logs an event **only** when it produces an event type the agent loop cannot: `send_chat` -> `chat`, `end_turn` -> `system`. Nothing else calls `ctx.log` | let every tool mirror its own effect into the log | `agent.py` already appends one `action` before `execute()` and one `result` after it, with the identifying arguments. Tools that logged again put every action into the log twice, and the rolling window (D6) then re-sent both copies to every villager on every turn - a duplicate you pay for once per turn for the rest of the session. Found by reading a `--fake` transcript, which is what `--fake` is for. |
| D26 | An agent's own past tool result renders as the first 240 chars of the observation | render a bare count (`n`, `chars`); render the full observation | A count is not actionable: `(result of your web_search: 5)` on turn 40 tells the agent nothing, so it re-runs the same search and pays twice. The full observation is unbounded and would defeat the window. 240 characters carries the first URL or the error message, and is bounded - the only property that matters inside a fixed window. |
| D27 | The offline cast is a committed module (`village/fake.py`, `--fake`), not a throwaway script | a `FAKE_MODE` branch inside `llm.py`; a scratch file that is not committed | Everything except the provider call is identical in a fake run, so the UI, the log, the scheduler and the deploy can all be demonstrated and debugged with no key, no balance and no network. The rejected alternative puts test-only code on the code path that spends real money, which is the last place to be clever. A test asserts the fake's signature still matches `llm.chat`, because the moment they drift an offline run stops proving anything about a live one. |
| D28 | `POST /api/stop` requires `X-Village-Token` once `VILLAGE_ADMIN_TOKEN` is set; `POST /api/message` stays open to anyone | leave both open (as on localhost); put both behind auth; drop the kill switch from the UI | The two write endpoints are not the same kind of thing. A spectator message is *content* the village is free to ignore - and it is the exhibit, so gating it would remove the reason to visit. Stopping is *control* over a run that costs money and cannot be resumed, so on a public URL an anonymous stop button is a griefing vector, not a feature. The token is empty by default, which is right on a laptop and wrong on a host - so `deploy/village-web.service` always sets one. |
| D29 | Deployed as two systemd units on one small VPS (`village-web` always on, `village-session` oneshot on a weekly timer) behind Caddy | Docker Compose; a PaaS (Fly/Render/Railway); one process doing both | The artifact is one Python process plus one SQLite file. Docker would add a build step, an image registry and a volume mount to arrive at the same place. A PaaS charges more for an always-on instance and makes a persistent local file the awkward case rather than the normal one. Oneshot-plus-timer, rather than a daemon, because a session is a *bounded job* - it has a turn cap and a spend cap and ending is the expected outcome. `Restart=always` on that unit would be a machine that spends money forever. Caddy over nginx because it renews TLS itself and proxies WebSockets with no extra directives. |
| D30 | A Tavily failure falls through to DuckDuckGo; a `TAVILY_API_KEY` still holding the `.env.example` placeholder counts as unset | let the Tavily error reach the agent as an observation; require a valid key | The failure this prevents is specific and was real in this repo: an unedited `TAVILY_API_KEY=tvly-...` is *truthy*, so the keyed path is taken, every call 401s, and the keyless fallback that exists precisely for this case never runs - silently, for an entire session, while the agents conclude the web has nothing on their question. A backend choice is an implementation detail; the agent asked for search results. DuckDuckGo keeps failing loudly, because it is the last resort and has nowhere to fall through to. `scripts/preflight.py` deliberately tests the key *directly* rather than through the tool, so the fallback cannot hide a dead key from a preflight. |
| D31 | A compaction is a private `compaction` event that **supersedes** every note written before it; `notes_for()` returns that text plus the notes written since | a separate `notes` table with a summary column; mutate or delete the prior `write_note` events; keep appending and truncate the oldest | Keeps D4's promise that the event log is the only state: nothing is edited, nothing is deleted, and the full pre-compaction history is still there to replay. It is also what makes the notes section of the prompt *bounded* rather than merely capped - a cap at 8 notes silently loses turn 3's decision at turn 40, whereas a compaction carries it forward in compressed form. Private, like `thought`: a summary written for one agent is not a message to the others, and putting it in their window would be paying for a second, worse copy of the chat they already saw. The call is a plain completion (`tools=[]`) because it must return text, not an action - a model given tools here reliably calls `write_note` instead of answering. Failure is logged as `compaction_failed` and the turn proceeds (D13's rule one layer up): a lost summary is a worse prompt, not a dead session. The call also writes a `thought` event with no prose, so `session_cost` and the eval queries count the money it spends. **Cost:** fidelity. Anything the agent's own summary drops is gone from its memory, even though the events are still in the log - which is exactly the trade retrieval would buy back (see future work). |

## Future work, with reasoning
What was scoped out, why, and what the upgrade path would be.

- **True concurrency.** Turn-based today (D3). The next step is *round-barrier*
  concurrency: all agents take their turn simultaneously against a frozen
  snapshot of the chat, with a barrier at the end of each round. That keeps
  writes single-threaded and ordering deterministic while overlapping the API
  latency, which is the actual bottleneck. The tradeoff it accepts is that
  agents cannot react *within* a round, so two villagers sometimes announce the
  same idea at once. Free-running concurrency multiplies with LLM
  nondeterminism and was not worth the debugging budget here.
- **Retrieval instead of compaction.** Memory is a rolling window plus
  self-written notes plus periodic compaction (D6). Embedding past events and
  retrieving the relevant ones would trade fidelity back for horizon. Worth it
  once sessions run long enough that agents visibly forget things they wrote.
- **GUI computer use.** The real AI Village gives each agent a Linux desktop and
  a screenshot loop. That is an *implementation* of agency, not its definition;
  the action space here is typed tool calls instead. A single sandboxed
  Playwright `browse()` tool is the natural bridge and was scoped out for time.
- **A real HTML extractor.** `_html_to_text` is regex-based. trafilatura or
  readability would give cleaner text, and is the upgrade to make if brief
  quality turns out to be limited by page parsing rather than by reasoning.
- **Per-model evaluation.** The log has everything needed to score which
  villager actually moved the goal forward (tool success rate, tokens per useful
  action, how often others acted on their chat messages). Not built; the data to
  build it is already being collected, which was the point of D4.
